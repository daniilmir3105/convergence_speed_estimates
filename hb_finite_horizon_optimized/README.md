# Heavy Ball: улучшенный finite-horizon эксперимент

Эта папка содержит отдельный эксперимент для диапазона

\[
1.1\leq\kappa=\frac{L}{l}\leq20\,000.
\]

Существующие реализации `hb` и `hb_finite_horizon_comparison` не изменяются.
Полный пайплайн запускается одним файлом `pipeline.py`.

## Что проверяет эксперимент

Эксперимент намеренно сохраняет исторический finite-horizon таргет:

\[
J_K=\frac{1}{MK}\sum_{m=1}^{M}
\log_{10}\left[
\max\left(
\frac{f(x_K^{(m)})}{f(x_0^{(m)})},10^{-300}
\right)
\right],
\qquad M=16,\quad K=300.
\]

Чем меньше `J_K`, тем лучше параметры отработали за 300 итераций. Формула
таргета не заменяется спектральным радиусом. 

Новый эксперимент отвечает на два разных вопроса:

1. Насколько точный минимум `J_300` совпадает с параметрами Поляка?
2. Насколько хорошо ML-пайплайн воспроизводит собственный finite-horizon
   минимум и реальное качество траектории?

Это различие принципиально: низкий `R²` относительно Поляка может быть либо
ошибкой ML, либо настоящим различием конечного и асимптотического оптимумов.

## Что изменено по сравнению с предыдущей реализацией

### 1. Exact oracle до обучения ML

Для стратифицированного набора значений `kappa` выполняется прямой поиск по
настоящему `J_300`, без первой ML-модели. Результат сохраняется в:

```text
data/oracle_diagnostic.csv
results/oracle_vs_polyak.png
```

Если уже oracle не похож на Поляка, увеличение числа деревьев не должно
искусственно исправлять это расхождение.

### 2. Быстрое точное вычисление старого таргета

При нулевом начальном импульсе каждая собственная координата после `K` шагов
равна начальной координате, умноженной на один скаляр. Код распространяет два
таких скаляра вместо полного массива из 16 траекторий. Это алгебраически тот
же результат, но вычисляется существенно быстрее.

### 3. Масштабирование таргета первой модели

Первая модель обучается предсказывать

\[
y_{ML}=\sqrt{\kappa}\,J_{300}.
\]

Для фиксированного `kappa` множитель положителен и одинаков для всех
кандидатов, поэтому положение минимума не меняется. Масштабирование только
делает малые различия при больших `kappa` заметнее для регрессора.

### 4. ML ранжирует, точный таргет принимает окончательное решение

Обратный поиск состоит из следующих этапов:

1. первая модель оценивает глобальную сетку;
2. выполняется локальное уточнение её лучшего кандидата;
3. лучшие кандидаты пересчитываются настоящим `J_300`;
4. выполняются два точных локальных уточнения;
5. только после этого полученная пара становится разметкой.

Поэтому небольшая ошибка forward-модели не обязана превращаться в ошибочную
метку для финальных моделей.

### 5. Финальные модели предсказывают устойчивые координаты

Вместо независимого предсказания сырой `alpha` используются две модели:

```text
(L, l) -> q
(L, l) -> beta
```

где

\[
q=\frac{\alpha L}{2(1+\beta)}.
\]

После предсказания восстанавливается

\[
\alpha=\frac{2q(1+\beta)}{L}.
\]

Значение `q` конструктивно ограничивается диапазоном `(0, 0.99999]`, поэтому
предсказанные `alpha` и `beta` не могут образовать асимптотически неустойчивую
пару. Внешними входами остаются только `L` и `l`; дополнительные признаки
вычисляются из них внутри `pipeline.py` и `predict.py`.

### 6. Проверяется реальная траектория

Итоговые модели сравниваются:

- с точными finite-horizon метками;
- с параметрами Поляка;
- по настоящему значению `J_300`;
- отдельно по диапазонам `kappa`.

## Зависимости

Используются уже применяемые в проекте библиотеки:

```text
numpy
pandas
scikit-learn
joblib
matplotlib
```

Первая модель — `HistGradientBoostingRegressor` из scikit-learn. Это
гистограммный градиентный бустинг, выбранный для ускорения обучения на
нескольких сотнях тысяч строк. Финальные модели используют обычный
`GradientBoostingRegressor`.

## Полный запуск

Команда выполняется из корня проекта:

```powershell
.\venv\Scripts\python.exe hb_finite_horizon_optimized\pipeline.py
```

Конфигурация полного запуска по умолчанию:

| Параметр | Значение |
|---|---:|
| Диапазон `kappa` | `[1.1, 20000]` |
| Группы forward-датасета | 2400 |
| Кандидатов в группе | 96 |
| Oracle-точек | 256 |
| Oracle-сетка | `64 x 64` |
| Пар для финальных моделей | 10000 |
| ML-сетка обратного поиска | `64 x 64` |
| Точное локальное уточнение | два раза по `17 x 17` |

Полный запуск может занять заметное время. В консоли выводится прогресс oracle
и обратного поиска.

## Быстрая проверка пайплайна

Эта команда предназначена только для проверки работоспособности, а не для
получения финальных метрик статьи:

```powershell
.\venv\Scripts\python.exe hb_finite_horizon_optimized\pipeline.py `
  --forward-groups 300 `
  --forward-candidates 48 `
  --forward-iterations 100 `
  --oracle-points 32 `
  --oracle-grid 24 `
  --oracle-refine 13 `
  --meta-pairs 500 `
  --meta-estimators 150 `
  --search-grid 24 `
  --predicted-refine 12 `
  --exact-top-k 12 `
  --exact-refine 9 `
  --batch-size 32
```

Быстрый запуск перезаписывает содержимое локальных папок `data`, `models` и
`results`. Перед финальным запуском отдельная очистка не требуется: файлы с
одинаковыми именами будут обновлены.

## Предсказание после обучения

Пример для `L=1000`, `l=10`:

```powershell
.\venv\Scripts\python.exe hb_finite_horizon_optimized\predict.py 1000 10
```

Скрипт выводит:

- предсказанные `alpha`, `beta` и `q`;
- признак устойчивости;
- теоретические параметры Поляка для сравнения.

## Основные результаты

После выполнения следует сначала открыть:

```text
results/metrics.json
results/oracle_vs_polyak.png
results/direct_models_vs_finite_labels.png
```

Особенно важны поля:

```text
metrics.oracle
metrics.forward
metrics.inverse_labels_vs_polyak
metrics.final.alpha_vs_finite_label
metrics.final.beta_vs_finite_label
metrics.final.performance_vs_polyak
metrics.final.performance_vs_finite_label
metrics_by_kappa
```

Интерпретация:

- высокий oracle `R²` против Поляка означает, что ML теоретически может
  восстановить похожие параметры при данном таргете;
- низкий oracle `R²` при хорошем `J_300` означает настоящее расхождение
  конечного и асимптотического критериев;
- высокий `R²` финальных моделей относительно finite-horizon меток означает,
  что прямая модель успешно воспроизводит решённую обратную задачу;
- `performance_vs_polyak.model_better_fraction` напрямую показывает, как
  часто итоговые ML-параметры лучше Поляка именно через 300 итераций.
